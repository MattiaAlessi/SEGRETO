# Rust Vs PyNaCl Benchmark

Since I didn't want to rely on the excuse *"Rust is fast because... is Rust"*, so I learned Rust thanks to youtube and wrote a [benchmark](../TEST/benchmark.py) to pit the module built in Rust ([crypto_core](../crypto_core/src/lib.rs)) against the library `PyNaCl` (written in C)  

## The Problem

Before checking who is faster, I needed to make sure both libraries were talking the same cryptographic language. If Rust encrypts a message and PyNaCl can't decrypt it, high speed is useless.

The benchmark script runs a cross-check test suite before measuring performances:  
- **AEAD (XChaCha20-Poly1305):** encrypting with Rust and decrypting with PyNaCl (and vice versa) yields identical ciphertexts and plaintexts
- **X25519 (Key Exchange):** public key generation and Diffie-Hellman shared secrets produce identical 32 bit keys
- **Ed25519 (Signatures):** signatures generated by `crypto_core` verify successfully under PyNaCl and vice versa
- **Argon2id & BLAKE2b:** identical derived keys and hash outputs for matching parameters.

## More details

### 1. Payload Encryption & Key Exchange (RUST is the winner)
For standard chat operations like encrypting short messages and establishing DH secrets the Rust extension is tipically **2x to 2.6x faster** than PyNaCl.  
So the final verdict as a peer-to-peer chat constantly performs key handshake and payload encryptions the Rust module gives a noticeable boost without letting our PC making the sounds of a V12 engine.

### 2. Signature Verification (RUST is the winner)
Ed25519 verification in Rust runs are **2.6x to 2.8x times faster** than with PyNaCl. 


### 3. Password Hashing with Argon2id (PyNaCl is the winner)
When deriving keys from passwords the PyNaCl library finish in **hals the time** respect Rust.  
However, since key derivation only happens **once at login**, taking ~200 ms is actually a feature, not a bug (it makes brute-forcing passwords harder for an attacker).

## Conclusion & Architectural Decision

We will proceed with **Rust** as our primary cryptographic engine because:
1. It outperforms `PyNaCl` in key exchange, chat message encryption/decryption, and signature verification.
2. It allows us to control low-level cryptographic operations directly inside our own codebase without relying on heavy external runtime dependencies.

> *(And mostly because having Rust in the repo makes the project look much cooler).*
